# Need U AI Lab — 목적과 구현 계획

작성일: 2026-10-11. 첫 버전은 개발자 컴퓨터에서 실행하는 내부 관리 도구다.

## 2026-10-12 추가 — Hugging Face 호스팅 모델 연결

Hugging Face Inference Providers 연결과 HF_TOKEN 설정 경로를 추가했다. 모델 이름을 저장하면
실제 라우터의 공개 Chat API 목록을 조회하고 사용 가능한 제공업체를 확인한다. 모델 이름만
입력하면 구조화 출력 지원 업체를 우선 선택해 `모델:제공업체`로 고정하며, 직접 지정한 조합은
제공 여부를 검증한다. 미제공 모델은 저장을 거절하고 기존 연결을 보존한다.

기본 연결은 `Qwen/Qwen3.5-9B:deepinfra`다. 2026-10-12 공개 목록 조회에서 291개 모델·제공업체
조합과 이 기본 모델의 구조화 출력 지원을 확인했다. 공개 목록 조회는 토큰 유효성이나 실제 추론을
검증하지 않는다. HF_TOKEN이 비어 있으므로 실제 HF 추론 호출은 아직 하지 않았다.

토큰은 프로세스 환경변수 또는 프로젝트 .env의 HF_TOKEN을 읽고 DB·브라우저·실행 이력에 저장하지
않는다. 키 미설정 상태에서도 공개 목록을 보여준다. 토큰·권한·결제 오류 안내를 추가했다. 제공업체가
구조화 출력을 미지원한다고 명시한 조합은 추출 역할에서 거절한다. 단위 테스트는 HF 프로토콜과
실제 니쥬 프롬프트·스키마·호출 경로를 대체 응답으로 검증한다.

전체 자동 테스트 292개 통과. 호스팅 API는 모델 품질 후보 선별에 쓰고, 최종 가중치 커밋·양자화·
GPU·vLLM 조건의 성능은 Runpod에서 별도로 검증한다. HF Hub 저장소와 제휴 업체 추론 API를
구분해 안내한다.

## 2026-10-12 추가 — Gemini 페르소나 자동 대화

고정 발화와 Gemini 합성 사용자 대화를 선택한다. 합성 사용자는 페르소나별 시스템 프롬프트와
실제 니쥬의 응답을 보고 다음 발화를 생성한다. 기존 서비스 Gemini API 연결과 키를 재사용하며
니쥬의 응답·추출 모델 선택과 독립적이다. 기대 추출·상품·쿼리·내부 프로필은 사용자 모델에
노출하지 않는다. 발화·호출·프롬프트 버전·지연을 기록하고 최대 턴·시간 상한·취소를 적용한다.
실험 이력에 전체 대화를 표시하며 고정 입력과 합성 대화의 비교 조건을 구분한다.

전체 283개 자동 테스트 통과. Gemini 사용자 모델과 LM Studio GPT OSS 20B를 실제 연결한
김소연 페르소나 5턴 검증은 7단계 완료, 추출 실패 0턴, 요약·추천 쿼리 생성 성공이었다.
이 검증은 연결·실행 확인이며 모델 품질 점수가 아니다. 검증 DB는 운영 보드 DB와 분리했다.

합성 사용자도 설정 밖 세부 경험을 만들어낼 수 있으므로 페르소나 준수 여부를 사람이 확인한다.
대화에서 공개되지 않은 취향은 추출 기대값에서 제외한다. 자연스러움 탐색은 합성 대화,
동일 입력의 회귀 비교는 고정 발화, 최종 품질 판단은 소수의 실제 사용자 대화 검토로 나눈다.

## 현재 운영 방향 — 소규모 검증 우선

응답·추출 모델과 크기는 미확정이다. 문서의 8B·1B·30B는 후보 또는 자원 산정 가정이다. 실제 서비스
프롬프트로 후보 2~3개를 중요한 상황 10~15개에서 비교한다. 대시보드의 테스트 실행과 보드의 목적에
검토할 상황 10개를 안내하며, 이는 자동 정답 평가셋이 아니다.

프롬프트·추출·프로필 병합·추천 쿼리 중 실패 지점을 먼저 확인하고 수정한다. 모델의 실패가 반복되고 더
큰 모델의 비용·지연이 부담될 때 파인튜닝을 검토한다. 페르소나 30개·AI Hub 대규모 데이터 가공· 학습
관리·GPU 관측은 현재 필수 범위에 넣지 않는다.

자유 Playground 실행 모드는 화면·API에서 제거했다. 과거 기록의 조회·내보내기는 유지하며 재실행은
지원하지 않는다. 니쥬 서비스 테스트가 기본이고, 초기 추출 smoke·제한된 동시성 테스트는 보조 도구다.
아래의 초기 계획에 남은 Playground 언급은 구현 이력이다.

니쥬 대화의 범위를 경험·가치관·관계·생활의 변화·선택의 이유·미래 계획까지 넓혔다. 새
관심사 추출 여부에 따른 강제 화제 전환, 추천 공백에 따른 소재 가중치, 자동 프로필 되비추기를
제거했다. 짧은 반응과 질문 없는 응답도 허용하며 사용자 발화의 맥락을 우선한다. 추천 준비 상태는 기존
종료 판단에만 사용한다. 추출 스키마를 확장하거나 모든 개인 정보를 새로 저장하지 않는다.

이번 변경은 전체 자동 테스트 271개와 브라우저의 프롬프트·안내·모드 표시로 검증했다. 실제 모델의 대화
자연스러움은 변경 전후의 동일 입력으로 별도 확인해야 한다.

## 2026-10-12 변경 — 실제 서비스 경로 연결

아래의 초기 계획에서 후속 범위였던 **실제 유스케이스 재생과 추천 쿼리 생성**을 구현했다.

- 기본 테스트 모드는 니쥬 서비스다. 실제 `ChatUseCases` / `ConversationService` / `ProfileMerger`와
  서비스의 프롬프트 빌더를 그대로 실행한다.
- `.env`와 프로세스 환경변수에서 역할별 모델·타임아웃·토큰 설정을 읽는다. 응답·추출 모델은 등록한
  로컬 연결로 대체할 수 있다. 선택은 실행 스냅샷이며 `.env`나 운영 세션을 수정하지 않는다.
- 판단 모델 경로는 `JUDGMENT_MODEL_BASE_URL`에 따라 후보 추출→판단 또는 직접 추출로 실행한다. 이번
  실험에서 판단을 꺼 직접 추출 모델만 검증할 수도 있다.
- 한 줄에 한 사용자 발화를 입력해 멀티턴을 진행하고, 실제 서비스의 입력 길이·종료 정책을 따른다. 매
  실행은 격리된 메모리 세션이다. 운영 Redis·MySQL에 연결하거나 쓰지 않는다.
- 실제 추천 API의 프로필 변환, 추천 신호·가이드 생성, 검색 쿼리 조합 함수를 사용한다. 쿼리 생성은
  규칙 기반이며 임의의 새 LLM 프롬프트로 대체하지 않는다.
- 추천 범위는 쿼리 생성까지만 / 실제 임베딩 / 실제 카탈로그 추천으로 선택한다. 실제 상품 추천은
  서비스의 임베딩·검색·랭킹을 재사용하고 DB 연결은 읽기 전용 트랜잭션으로 제한한다.
- 실제 요청 메시지·추출 스키마·원본 결과·병합된 프로필·추천 쿼리·제외/선호 임베딩 입력을 기록한다.
  추출 fallback, 요약 미생성, 정책에 의한 조기 종료도 구분해서 표시한다.
- 서비스 소스 전체를 실행 코드 해시에 포함하고, 환경 설정이 대기 중 달라지면 실행을 중단한다.
  자격증명 값과 DB DSN은 설정 화면·이력·export에 노출하지 않는다.
- 세션 모드는 실행 단계 성공률과 대화 턴 p50/p95를 구분한다. 자동 gold 정답 평가와 페르소나 30개,
  여러 세션 혼합 부하·GPU·비용 수집은 아직 후속 범위다.
- 검증: 전체 자동 테스트 270개 통과. 브라우저에서는 별도의 HTTP 테스트 서버로 멀티턴 실행·쿼리
  생성·임베딩·이력 비교를 확인했다. 실제 모델 품질과 운영 카탈로그 연결은 아직 측정하지 않았다.

서비스 모드 실행 안내는 [대시보드 README](../dashboard/README.md)를 따른다. 아래의 초기 버전에서
"`.env`를 읽지 않음", "서비스 전체 경로 미구현"은 이제 보조 단일 모델 테스트에만 해당한다.

## 1. 왜 만드는가

V2에서는 모델 가중치를 직접 서빙한다. 모델 이름만 고르는 것이 아니라 프롬프트, 정밀도, 런타임,
하드웨어, 동시 처리 설정의 조합을 선택해야 한다. 이 보드는 같은 입력과 평가 기준으로 후보를
실행하고, 실패 사례와 측정값을 남겨 그 선택을 재현할 수 있게 한다.

사용자는 AI 개발자와 운영 담당자다. 주된 사용 흐름은 다음과 같다.

1. LM Studio 또는 Ollama에서 모델을 실행하고 보드에 엔드포인트를 등록한다.
2. 연결 검사로 모델 ID를 확인하고, 실제 프롬프트로 출력과 측정 정보를 확인한다.
3. 고정 평가 사례로 부정 표현, 선호·비선호, 사용자 정정을 검증한다.
4. 같은 조건을 복사해 다른 모델을 실행하고 결과를 비교한다.
5. 후보를 RunPod에 배포한 뒤 같은 평가를 반복하고 대상 GPU의 부하를 측정한다.
6. 품질·지연·오류·비용 기준을 통과한 구성을 운영 후보로 기록한다.

보드의 첫 목적은 **모델 선택과 검증**이다. 운영 연결 후에는 장애와 자원 사용 상태를 관측하는 목적을
추가한다. 테스트 이력의 성공률은 운영 트래픽 성공률과 다르며, 첫 버전에서는 운영 지표를 수집하지
않는다. 연결 검사도 추론 품질이나 모델 적재 완료를 보장하지 않는다.

## 2. LM Studio와 Ollama의 역할

두 도구는 모델을 실행하는 런타임이다. 보드는 해당 도구의 HTTP API를 호출하는 테스트 클라이언트다.
사용자가 설치·다운로드·적재한 모델을 대상으로 하며 보드가 모델을 다운로드하거나 GPU를 생성하지
않는다.

| 환경                      | 기본 API URL                | 확인할 것                                           |
| ------------------------- | --------------------------- | --------------------------------------------------- |
| LM Studio                 | `http://127.0.0.1:1234/v1`  | 한국어 출력, 프롬프트, 구조화 출력, 로컬 지연       |
| Ollama                    | `http://127.0.0.1:11434/v1` | 동일 평가 반복, 모델별 출력과 로컬 처리량           |
| RunPod / OpenAI 호환 서버 | 배포한 URL                  | 실제 GPU 처리량, 네트워크 포함 지연, 운영 후보 품질 |

공통 연결은 `/models`와 `/chat/completions`다. 호환 API는 제공 기능의 부분집합이므로 구조화 출력과
stream usage 등의 지원 여부는 실제 호출로 검증한다. 지원하지 않는 옵션을 자동으로 삭제해 테스트
조건을 바꾸지 않는다.

로컬 지연을 RunPod 성능으로 환산하지 않는다. 같은 모델 계열이라도 GGUF/MLX/BF16, 양자화, chat
template, 런타임과 하드웨어가 바뀌면 품질·속도를 다시 확인한다. Ollama 로컬 서버에 연결하더라도
클라우드 모델을 선택하면 로컬 추론이 아닐 수 있으므로 모델 설정에 실행 환경을 정확히 남긴다.

## 3. 현재 코드에서 확인한 것

- `app/`은 실제 서비스 FastAPI다. 응답·추출·상품 설명·임베딩 설정이 분리되어 있다.
- 기존 게이트웨이는 텍스트를 반환하고 usage 등 응답 메타데이터를 보존하지 않는다.
- 모델 스트리밍 메서드는 있지만 현재 대화 HTTP API는 완성된 JSON 응답을 반환한다.
- 판단 모델은 별도의 System One 계약이다. 일반 채팅 API로 대체했다고 가정하지 않는다.
- 기존 인프라 문서는 두 모델을 같은 GPU에 배치하고 Grafana로 관측하는 방향이다.

첫 버전은 `app/`의 동작과 API 계약을 바꾸지 않는다. 실험용 HTTP 클라이언트는 메타데이터를 보존해야
하므로 관리 앱에 둔다. 실제 니쥬 파이프라인 재생은 다음 단계에서 기존 유스케이스를 재사용한다.

## 4. 첫 버전의 범위와 완료 기준

| 기능               | 완료 기준                                                               |
| ------------------ | ----------------------------------------------------------------------- |
| 목적 안내·현황     | 보드의 역할, 로컬/운영 차이, 실제 실험에서 나온 통계와 미수집 상태 표시 |
| 연결 관리          | 두 로컬 런타임 기본 등록, 사용자 엔드포인트 등록·수정, 모델 목록 검사   |
| Playground         | 사용자 프롬프트를 실제 모델에 요청하고 출력·시간·usage 표시             |
| 고정 품질 평가     | 소규모 공개 fixture에 대해 스키마 및 정답 일치 판정, 실패 사례 표시     |
| 제한된 부하 테스트 | 요청 수·동시성·시간 상한, 진행률·취소, 성공/실패 개별 기록              |
| 결과 비교·내보내기 | 최대 두 실행의 설정과 측정값 비교, 조건 복사, JSON·CSV 다운로드         |
| 별도 실행 워커     | 웹 프로세스 밖에서 테스트 실행, 새로고침 후에도 이력 보존               |

품질 fixture는 사람이 검토할 수 있는 8개의 초기 사례다. 이는 벤치마크 전체나 니쥬 서비스 품질 점수가
아니다. JSON 형식 준수와 내용 정답 일치를 별도로 표시한다. 대화 자연스러움은 출력 원문을 보고 사람이
판단한다. 자동 LLM 채점은 첫 버전에 없다.

## 5. 측정 정의

- 완료시간: 워커가 HTTP 호출을 시작한 시점부터 스트림 종료까지의 경과시간. 네트워크 포함.
- 첫 출력 청크 시간: 첫 번째 비어 있지 않은 `content`를 수신할 때까지의 시간. thinking 청크는
  포함하지 않는다. 정확한 서버 TTFT가 아니므로 UI에서 청크 시간으로 표기한다.
- 토큰 수: provider가 반환한 usage만 사용한다. 누락되면 미측정이며 글자 수로 토큰을 추정하지 않는다.
- 출력 처리량: 완전한 usage가 있는 성공 요청의 출력 토큰 합 / 테스트 전체 경과시간. 누락이 있으면
  실행 전체 토큰 처리량은 미측정으로 표시한다.
- 지연 p50/p95: 성공한 요청의 실제 표본으로 계산한다. 표본 수를 같이 표시하며 작은 표본의 p95를 운영
  SLO 판정에 쓰지 않는다. 실패 요청은 성공 지연 분포에서 제외하되 오류율에서 빠뜨리지 않는다.
- 품질: 스키마 통과와 fixture 정답 일치의 비율. 실패한 요청도 평가 대상의 분모에 포함한다.
- 부하 방식: 고정 동시성의 closed-loop 테스트. 초당 요청 유입량을 고정한 open-loop 부하와 다르다.
- 워커 준비 여부와 prefix cache 상태는 자동 추정하지 않는다. 사용자가 실험 메모로 남긴다.
- GPU 사용률, VRAM, 콜드스타트, 청구 비용은 수집기를 붙이기 전까지 미수집이다.

## 6. 구성과 데이터

```text
dashboard/           정적 HTML/CSS/JS 관리 화면, 별도 빌드 의존성 없음
admin_api/           별도 FastAPI, 연결·작업·결과 API, SQLite 저장소
benchmarks/          별도 워커와 고정 품질 fixture
app/                 기존 서비스
.local/ai-lab/       개발용 SQLite와 워커 잠금 파일, Git 제외
```

첫 버전은 로컬 SQLite 작업 큐와 단일 워커다. 기존 PostgreSQL·Redis 서비스에 영향을 주지 않고 실행할
수 있다. 운영 공용 보드로 전환할 때 PostgreSQL·Redis 작업 큐, 관리자 인증, 역할별 접근, OTel/Grafana
연동으로 확장한다. 현재 실행 명령은 loopback에만 바인딩한다.

각 실행에는 연결 설정 스냅샷, 모델 ID·revision·정밀도·하드웨어 메모, 실행 조건, 입력, fixture
버전·해시·실행 시점의 사례 원본, 코드 revision·소스 해시, 시간·usage·출력·오류를 저장한다. API key는
저장하거나 화면으로 보내지 않고 관리 프로세스와 워커의 환경변수 이름으로 참조한다. 셸 `.env`를
자동으로 읽지 않아 서비스 비밀정보를 관리 앱에 불필요하게 가져오지 않는다.

Playground 입력과 출력은 로컬 이력에 남는다. 실제 사용자 대화 대신 합성·익명화 데이터로 테스트한다.
미처리 대기 작업과 실행 결과에는 삭제 기능을 제공한다.

작업마다 최대 100요청·동시 8·300초·출력 512토큰을 제한한다. 화면에서 총 요청 수와 최대 출력 예산을
확인할 수 있다. 취소 시 현재 클라이언트 요청도 중단하지만 provider의 연산·과금 즉시 종료는 보장하지
않는다. 원격 서버의 비용은 별도 청구 데이터를 연결해야 한다.

## 7. 후속 구현 순서

1. 현재 서비스 프롬프트와 유스케이스로 대화→취향 변화→분석→추천을 재생한다.
2. 추출·정정·철회·추천의 검토된 gold set을 30~50개 이상으로 확대한다.
3. RunPod에서 응답·추출 모델의 단독 부하와 혼합 부하, 긴 대화, 워커 콜드스타트를 측정한다.
4. vLLM `/metrics` + GPU 수집기 + 애플리케이션 tracing을 Grafana로 보낸다.
5. 운영 오류, 모델별 fallback, 비용·청구시간과 배포 후보 판정 기준을 연결한다.

자동 배포·모델 교체·RunPod 자원 생성/삭제는 이후 범위다. 합성 데이터 테스트와 실제 모델 실행 검증을
구분해서 보고한다. 모델이 실행되어 있지 않으면 미연결 상태로 전달한다.

  관계없는 파일은 수정하지 않았다.
