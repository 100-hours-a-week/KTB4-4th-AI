# chat/ — 대화 하네스

터미널에서 직접 유저 역할을 하면서 대화 로직을 테스트한다.

```bash
# LM Studio > Developer > Start Server
cp chat/.env.example chat/.env      # 모델 이름 맞추기
python3 chat/run.py                 # 기본
python3 chat/run.py -v              # 지시문·델타 원본까지
python3 chat/run.py --no-extract    # 대화만 (추출 끄고)
python3 chat/run.py --json out.json # 마무리 결과를 파일로
```

의존성 없다. `/state` 현재 상태 · `/profile` 계약 형태 프로필 · `/finish` 마무리 · `/quit` 종료.

## 어디까지 하는가

[1단계 최종본](../docs/wiki/모델-API-설계.md)의 내부 처리 순서 중 **임베딩 직전까지**다.

```
세션 상태를 프로필로 확정            ← State.to_profile()
→ query 역할 항목을 검색 문장으로 재작성  ← finalize._rewrite()
→ lifestyle 에서 파생 쿼리 (self 전용)   ← finalize._rewrite() derived
→ 요약문 생성 (친구 공개 항목만)         ← finalize._summarize()
────────────────────────────────── 여기까지가 이 하네스
→ 검색 문장 임베딩
→ 벡터 검색 · 하드필터 · 스코어 · 다양성 선별 · 이유 생성
```

세션 저장소(Redis)도 벡터 DB도 붙이지 않는다. 상태는 프로세스 메모리에 있고,
`queries` 는 **임베딩 단계에 넘어갈 입력**까지만 만들어 보여준다.
쓰는 건 모델 두 개(응답·추출)와 마무리 호출 두 개(재작성·요약)뿐이다.

## 한 턴에 일어나는 일

```
유저 발화
   ↓
① policy.decide(state)        서버가 이번 턴 목표를 정한다 — 순수 로직, LLM 안 씀
   ↓
② 응답 모델 (스트리밍)         목표를 지시로 받아 문장 하나를 만든다
   ↓  ← 유저가 기다리는 구간은 여기까지
③ 추출 모델 (구조화 출력)      이번 발화에서 델타 JSON 을 뽑는다
   ↓
④ state.apply(delta)          서버가 병합·정정·방출한다
```

## 파일

| 파일 | |
|---|---|
| `policy.py` | **이번 턴에 뭘 물을지 정한다.** 여기가 핵심 |
| `schema.py` | 칸 정의, 파생 규칙, 병합·방출 |
| `prompts.py` | 프롬프트 조립. 캐시 살리는 순서를 지킨다 |
| `llm.py` | LM Studio 호출 (스트리밍 / JSON 스키마) |
| `finalize.py` | 대화 종료 후 — 프로필 확정, 검색 문장 재작성, 요약문 |
| `run.py` | 터미널 루프 |
| `web.py` · `ui.html` | 같은 걸 브라우저에서 (`python3 chat/web.py`) |

## 서버가 하는 일 / 모델이 하는 일

| | |
|---|---|
| **서버** | 무엇을 물을지, 언제 그만할지, 방식을 바꿀지, 항목 병합·정리 |
| **모델** | 그 지시대로 문장 하나 만들기 / 발화에서 항목 뽑기 |

모델에게 "알아서 판단해라"를 시키지 않는다. 그래서 응답 시스템 프롬프트가 400자밖에 안 된다.

## 목표 전환 규칙 (policy.py)

위에서부터 순서대로 본다.

| 순서 | 조건 | 목표 |
|---|---|---|
| 0 | 첫 턴 | `OPENING` — 일과를 가볍게 묻는다 |
| 1 | 20턴 도달 / 발화 길이가 계속 줄어듦 | `WRAP` |
| 2 | 조건 충족 + 8턴 이상 + want 를 물어본 적 있음 | `WRAP` |
| 3 | 검색용 항목 3개 미만 | `INTEREST` |
| 3' | 위 + 직접 질문 2회 했는데 아직 0개 | `INTEREST_VIA_ROUTINE` — **한 번 바꾸면 안 돌아간다** |
| 4 | 싫어하는 것·제약 0개 (3턴 이후) | `DISLIKE` |
| 5 | want 항목 0개 (5턴 이후 또는 검색용 3개 참) | `WANT` |
| 6 | 확신 0.6 이상이 2개 미만 | `DEEPEN` |

**3' 이 이 하네스를 만든 이유다.** 취향을 직접 물으면 대답 못 하는 사람이 있다.
서버가 "두 번 물었는데 아무것도 안 나왔다"를 세고 있다가 일과에서 캐는 방식으로 바꾼다.

**2번에 want 조건이 붙은 이유** — want 가 0개면 선물 목록이 통째로 빈다.
다른 조건을 다 채웠어도 한 번은 물어보고 끝낸다.

## 확인할 것

돌리면서 볼 것들.

- 목표 전환이 제때 일어나나 (특히 `INTEREST` → `INTEREST_VIA_ROUTINE`)
- 지시를 받고 모델이 그대로 하나, 아니면 딴소리하나
- 지시문을 사용자에게 그대로 읽어주지는 않나
- 추출이 유저가 말한 것만 넣나, 지어내지 않나
- 같은 항목을 다른 칸에 넣지 않나 (`interests` vs `hobbies`)
- 첫 글자까지 몇 초 걸리나 (턴마다 찍힌다)
- `/profile` 이 계약의 `TasteProfile` 모양 그대로 나오나
- 취향 항목이 **상품 설명 어휘**로 바뀌나 ("짐 많아지는 게 싫어요" → "가볍고 부피 작은 ~")
- 생활 맥락에서 파생된 쿼리가 `self` 로만 가나 (친구에게 사정이 새지 않아야 한다)
- `unaffordable` 쿼리에 선물 가중(1.5 / 1.4 / 1.15)이 붙나
