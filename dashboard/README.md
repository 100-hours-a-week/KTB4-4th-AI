# Need U AI Lab

모델 선택과 운영 검증을 위한 로컬 관리 앱. 목적·범위는 [계획 문서](../docs/ai-dashboard-plan.md)를
따른다.

니쥬 서비스의 실제 멀티턴 대화·취향 추출·프로필 병합·추천 쿼리 생성 경로를 실행한다. 환경변수 기본
설정과 대화 스타일·역할별 로컬 모델을 선택할 수 있다. 실제 임베딩·카탈로그 추천은 실행 범위로
선택한다. 취향 추출 smoke 평가 8개, 제한된 동시성 테스트와 이력 비교도 지원한다. 운영
트래픽·GPU·Runpod 비용 수집은 후속 범위다. 서비스의 대화 프롬프트를 직접 재사용한다.

흰색·파란색 카드형 대시보드에서 상세 페르소나 30개와 실제 API 채팅 세션도 제공한다.

## 실행

저장소 루트에서 기존 Python 환경을 사용한다. 설치가 필요하면 `uv sync --dev`를 먼저 실행한다. 두
터미널에서 각각 실행한다.

```bash
uv run uvicorn admin_api.main:app --host 127.0.0.1 --port 8010
```

```bash
uv run python -m benchmarks.worker
```

브라우저: <http://127.0.0.1:8010>. 기본 바인딩은 loopback이며 공용 운영 서버로 공개하지 않는다. 별도
프론트엔드 빌드는 필요 없다. `.local/ai-lab/`의 SQLite에 결과가 보존된다. `AI_LAB_DB`를 지정하면
서버와 워커 모두 같은 절대 경로를 사용해야 한다. 워커는 단일 프로세스만 실행할 수 있으며 파일
잠금으로 중복 실행을 막는다.

직접 대화 테스트는 관리 API만으로 실행하며 워커가 필요 없다. 고정 시나리오·추출 smoke·동시성 실험은
워커를 함께 실행한다. 관리 API는 기본 단일 프로세스로 실행한다. 다중 `--workers`는 세션 요청 잠금을
공유하지 않으므로 이 로컬 보드에서 지원하지 않는다.

코드를 수정한 뒤에는 관리 API와 워커를 함께 재시작한다. 서로 다른 코드 버전이면 새 테스트는 실패
상태로 남기고 모델을 호출하지 않는다.

## 첫 테스트

1. LM Studio Developer 탭에서 서버와 모델을 실행하거나 Ollama를 실행한다.
2. 보드의 모델 연결에서 기본 연결을 선택하고 연결 검사를 한다.
3. 목록의 실제 모델 ID를 입력하고 연결 저장을 누른다.
4. 니쥬 서비스 테스트에서 응답·추출 연결을 선택하고 고정 사용자 발화를 입력해 실행한다.
5. 같은 발화·스타일·추천 범위로 후보 2~3개를 비교한다. 초기 추출 평가와 동시성 테스트는 보조로 쓴다.
6. 실험 이력에서 조건을 복사하고 연결을 바꿔 다른 후보를 실행한다.
7. 두 이력을 선택해 결과 비교에서 확인한다.

이전 자유 단일 요청 Playground는 제거했다. 과거 실행 기록은 조회·내보내기할 수 있지만 해당 모드로 새
작업을 만들거나 조건을 복사해 재실행할 수 없다. 예전 `chat/` 프로토타입은 현재 저장소에 없다.

## Hugging Face Inference Providers 연결

1. [Hugging Face 토큰 설정](https://huggingface.co/settings/tokens)에서 Fine-grained 토큰을 만들고
   `Make calls to Inference Providers` 권한을 선택한다.
2. 프로젝트 `.env`에 `HF_TOKEN=발급한값`을 직접 입력한다. 키는 브라우저나 연결 SQLite에 저장하지
   않는다. 프로세스 환경변수 HF_TOKEN이 있으면 `.env`보다 우선한다. 기존 Gemini 키는 유지한다.
3. [결제 설정](https://huggingface.co/settings/billing)에서 사용 가능한 크레딧을 확인한다. 유료
   추론은 사용량에 따라 청구되며 PRO 가입이나 별도 제공업체 키가 이 연결의 필수 조건은 아니다.
4. 관리 API와 워커를 새 코드로 재시작한다. 모델 연결의 **Hugging Face API** 버튼으로 기본 연결을
   연다. URL은 `https://router.huggingface.co/v1`, 키 환경변수 이름은 `HF_TOKEN`이다.
5. **연결 검사 · 모델 목록**으로 현재 제공 중인 `모델:제공업체` ID를 조회한다. 기본 연결은
   `Qwen/Qwen3.5-9B:deepinfra`이며 제공 상태는 바뀔 수 있으므로 목록에서 다시 확인한다.
6. 모델 이름만 입력해 저장하면 현재 Chat API 목록을 확인하고 구조화 출력 지원 제공업체를 우선 선택해
   `모델:제공업체` ID로 저장한다. 원하는 제공업체를 붙이면 그 조합을 확인해 고정한다. API 미제공
   모델은 저장을 거절한다. 이후 대화/시나리오의 응답·추출 역할에 해당 연결을 선택한다. JSON Schema
   지원이 명시적으로 없는 제공업체는 추출 역할에서 거절한다. 미확인은 실제 호출로 확인한다.
   로컬/호스팅 모델을 역할별로 섞을 수 있으며 Gemini 페르소나는 별도로 유지한다.

토큰 없이도 공개 모델 목록은 조회한다. 이때 `HF_TOKEN 미설정`을 표시하고 추론은 진행할 수 없다. 목록
조회는 토큰 유효성·과금·실제 추론·니쥬 JSON Schema 성공을 검증하지 않는다. 401은 토큰, 403은
권한·모델 접근, 402는 추론 크레딧/결제 설정을 확인한다. 모델별 접근 동의가 요구되는 경우 모델
페이지에서 필요한 접근 권한을 확인한다.

공정한 비교에는 모델뿐 아니라 제공업체도 고정한다. 호출에 사용한 ID와 제공업체의 공개 지원 정보는
실행 설정에 기록한다. 호스팅 가중치 커밋·정밀도·GPU 정보는 공개 또는 확인 전까지 미확인으로 둔다.
Hugging Face API는 모델 품질 후보를 넓히는 데 유용하지만, 최종 Runpod 양자화·GPU·vLLM 버전의
품질·지연·처리량을 보장하지 않는다. 같은 고정 입력으로 후보를 선별한 뒤 실제 배포 환경에서 다시
측정한다.

연결 코드는 준비돼 있어도 실제 토큰이 없으면 유료 추론 검증을 완료했다고 표시하지 않는다.

Hugging Face Hub는 가중치 저장소다. 이 연결은 Hugging Face의 라우터를 통해 제휴 업체의 추론 서버를
호출한다. Hub 원본의 특정 커밋을 직접 다운로드해 서빙하는 것과 구분한다.

## Colab GPU 모델 연결

코랩은 Transformers로 모델을 GPU에 직접 로드하고, FastAPI + ngrok 연결만 유지한다. vLLM을 설치하거나
실행하지 않는다. 테스트 입력·니쥬 프롬프트·대화·추출·평가·결과 저장은 로컬 AI Lab에서 처리하고,
추론은 코랩 GPU에서 실행한다. 모델 로드만으로 로컬에서 코랩의 Python 객체에 접근할 수는 없으므로
작은 API 연결이 필요하다.

1. 모델 연결 화면에서 **코랩 노트북 다운로드**를 누르고 Colab에 업로드한다. 원본은
   [`notebooks/ai_lab_colab.ipynb`](../notebooks/ai_lab_colab.ipynb)이다. 기존 노트북에 Secrets를
   등록했다면 수정본의 셀을 기존 노트북에 복사해도 된다. 저장소 파일 변경은 Drive의 노트북을 자동
   변경하지 않는다.
2. GPU 런타임을 선택하고 Secrets의 `NGROK_AUTHTOKEN`, `AI_LAB_COLAB_KEY`, `HF_TOKEN`에 노트북 접근을
   허용한다. 로컬 `.env`의 `AI_LAB_COLAB_KEY`는 코랩과 같아야 한다. 키 값은 코드·출력·연결 SQLite에
   넣지 않는다. 관리 API·워커를 로컬에서 재시작한다.
3. `MODEL_IDS`를 설정한 뒤 **라이브러리·Secrets 준비 → 모델 로드 → API 연결** 셀을 실행한다. 기본
   Qwen3-8B를 유지한다. 두 모델 예시는 주석으로 제공하며 VRAM을 확인한 뒤 선택한다.
   모델·토크나이저는 실제 Hub commit으로 고정한다. 모델 로딩은 2번 셀에서 한 번만 진행하고 3번 셀은
   이미 로드된 객체를 사용한다. 원본 BF16/FP16용이며 AWQ 등의 양자화 모델은 별도 로더가 필요하다.
4. **Colab GPU 연결**에 출력된 `base_url`, `model`, `revision`, `precision`, `hardware`를 저장한다.
   URL은 `https://.../v1`이며 Colab 노트북 URL이 아니다. 여러 모델을 로드하면 같은 API URL로 연결을
   각각 등록하고 모델 ID를 구분한다. 연결 저장 → 연결 검사 후 응답·추출 역할에서 선택한다.
5. 모델 추론만 코랩에 두려면 판단 끄기를 선택하고 추천 범위를 쿼리 생성으로 둔다. 페르소나 자동
   대화의 사용자 역할은 기존 별도 모델 설정을 사용한다.

API는 Bearer 키로 모든 경로를 보호하며 `/v1/models`, `/v1/chat/completions`만 제공한다. 일반 응답과
SSE 스트리밍·usage를 지원한다. JSON Schema는 프롬프트에 추가하고 생성 완료 후 검증한다. 실패를
오류로 반환하며 토큰 생성을 스키마로 강제하지 않는다. 실제 니쥬 스키마로 테스트해야 한다. API 원본
코드는 [`notebooks/colab_transformers_api.py`](../notebooks/colab_transformers_api.py)이며 배포 파일
없이 사용할 수 있도록 같은 코드가 노트북에 포함돼 있다.

모델별 요청은 한 번에 하나씩 처리하며, 서로 다른 모델은 같은 GPU를 각 스레드에서 공유한다.
Transformers 방식으로 품질·속도를 측정하므로 최적화된 배포 런타임의 처리량을 확정하지 않는다. 응답의
`timings.server_first_token_ms`는 서버의 첫 생성 토큰까지의 시간이며, 단어 단위로 모일 수 있는
클라이언트 첫 내용 청크와 다르다. 현재 AI Lab 서비스 경로는 이 서버 timing을 저장하지 않는다. GPU
사용률·컴퓨팅 단위·비용은 자동 수집하지 않는다. 실제 A100 로딩·추론은 코랩에서 검증한다.

`stop_colab_api()`는 API·터널만 종료하고 모델은 GPU에 남긴다. 모델을 다시 로드하거나 자원을
반환하려면 Colab에서 런타임을 다시 시작하거나 연결 해제 및 런타임 삭제를 선택한다. 런타임·터널
재시작 후에는 출력 URL을 기존 연결에 다시 저장하고 새 대화·실험을 만든다. 이력의 이전 스냅샷은
유지한다.

공식 참고: [Transformers 채팅 템플릿](https://huggingface.co/docs/transformers/en/chat_templating),
[스트리밍 안내](https://huggingface.co/docs/transformers/en/internal/generation_utils#streamers),
[ngrok Colab 연결](https://ngrok.com/docs/using-ngrok-with/googleColab),
[Colab 사용 조건](https://research.google.com/colaboratory/faq.html).

## 직접 채팅 실행

1. 모델 연결에서 Ollama 또는 LM Studio의 실제 모델 ID를 저장한다.
2. 대화 테스트에서 응답·추출 모델을 각각 선택한다. 완전히 로컬로 진행하려면 판단 모델을 끈다.
3. 대화 이름과 선택 사항인 페르소나 가이드를 지정하고 세션을 시작한다.
4. 메시지를 직접 보내며 오른쪽의 프로필·검색 쿼리·원본 요청 프롬프트·추출 스키마를 확인한다.
5. 분석·대화 완료로 요약하고 세션을 종료한다. 종료 후에는 새 세션을 시작한다.

채팅은 `ChatUseCases`·`ConversationService`를 시나리오 실행과 공유한다. 응답과 추출은 실제
서비스처럼 병렬 처리한다. 운영 Redis·MySQL은 사용하지 않고 대화 상태·이력·모델 호출을 로컬 SQLite에
저장한다. 같은 탭에서 새로고침하면 선택한 대화를 다시 열며 API를 재시작한 뒤에도 대화 목록에서
복원할 수 있다. 세션의 원래 TTL·20턴·500자 계약을 적용한다. 같은 세션의 중복 요청은 거절하고 동시
채팅 요청은 최대 2개다. 설정·코드가 변경되면 기존 대화의 새 호출을 막고 새 세션을 요구한다.

직접 채팅은 추천 쿼리 생성까지 실행한다. 임베딩·카탈로그 검색은 시나리오 실행에서 선택한다. 응답이
생성됐더라도 추출 실패는 별도 경고와 원본 호출 기록으로 남긴다.

## 상세 페르소나 30개

기존 페르소나 10명의 원래 나이·직업·ID를 유지하고 세부 설정을 보강했다. 20~26세 학생·사회
초년생·프리랜서·취업 준비생 10명과 27~34세 직장인·경력직 10명을 추가해 총 30명으로 구성한다.
생활·주거·소유물·예산·말투를 포함해 서로 다른 맥락에서 취향을 확인하며 목록과 상세에서 기존/추가
그룹을 구분한다.

페르소나의 **시나리오로 실험**은 기본적으로 Gemini 자동 대화 설정을 연다. 실행 폼에서
`Gemini 페르소나 자동 대화` 또는 `고정 발화`를 선택한다. 자동 대화는 최대 10턴(1~20턴 선택)의 가상
사용자와 실제 니쥬 모델이 번갈아 대화한다. Gemini는 페르소나의 생활 맥락·가치관·미래 계획· 알려진
사실과 니쥬의 실제 응답만 본다. 기대 추출·추천 상품·쿼리 정답과 니쥬의 내부 프로필은 사용자 역할
모델에 전달하지 않는다. 알려진 사실은 반드시 공개해야 하는 대본이 아니다.

사용자 역할은 `.env`의 `PERSONA_MODEL_BASE_URL` / `PERSONA_MODEL_NAME`으로 별도 고정한다. 현재
예시는 OpenRouter의 `google/gemini-3.5-flash-lite`이며,
`PERSONA_MODEL_API_KEY_ENV=OPENROUTER_API_KEY`로 기존 OpenRouter 키를 직접 사용한다. 응답·추출
역할의 코랩 연결·로드 모델·`MODEL_API_KEY`를 바꿔도 사용자 역할의 API 주소·모델·키는 유지된다. 전용
키가 없으면 코랩 키로 대체하지 않고 설정 오류를 반환한다. 페르소나 설정을 생략한 기존 환경에서는
응답·추출 중 Gemini 연결을 찾는 이전 동작을 유지한다. 코랩으로 옮길 때는 전용 설정을 명시한다.
발화는 500자 이하이고, 사용자가 종료하거나 서비스가 종료하면 조기 중단한다. 요청 실패·형식 오류 시
실행 실패를 기록하며 고정 대본으로 대체하지 않는다. 기존 실행 취소·전체 시간 상한을 적용한다. 사용자
모델의 호출도 `persona` 역할로 프롬프트·응답·토큰·지연을 기록하고 실행 manifest에 프롬프트 버전을
보존한다.

합성 대화는 자연스러운 흐름을 탐색하기 위한 평가 보조다. 고정 입력 비교와 구분해서 보고, 추출 평가는
페르소나가 실제 공개한 발화만 근거로 한다. Gemini가 설정을 지켰는지도 함께 검토한다. 자동 품질
채점·실제 사용자 검증을 대체하지 않는다. 최종 모델 비교에는 같은 조건의 반복 실행과 고정 시나리오를
함께 사용한다. 외부 API 사용량은 과금될 수 있다.

실험 현황 또는 페르소나에서 합성 인물을 선택하면 나이·직업·생활 맥락·가치관·미래 계획·추천 검토
상황·고정 5턴·기대 추출·쿼리 소재·제외 조건을 볼 수 있다. 시나리오로 실험은 발화를 실행 폼에 채우고,
직접 대화는 해당 가이드를 연결한 새 채팅 설정으로 이동한다. 실제 사용자의 개인정보가 아니다.

기대 결과와 추천 후보 예시는 사람의 검토 기준이며 자동 정답 점수나 실제 검색된 상품이 아니다.
페르소나 원본을 실행 manifest와 채팅에 스냅샷으로 저장해, 시나리오를 바꿔도 이전 검토 기준을
보존한다. 발화를 편집하면 원본 기대 결과의 적용 여부도 직접 확인한다. 통계는 최근 100개 실행 이력
기준이다.

## 기대 추천 쿼리와 비교

페르소나 상세에 검색 공간(content/usage/gift)·추천 대상(self/gift)별 기대 문장과 핵심 조건·동의어를
표시한다. 시나리오 결과의 전체 비교와 턴별 결과, 직접 대화의 추출 패널에서 가장 가까운 실제
쿼리·반영 조건·누락 조건을 확인한다. 결과 비교에는 최종 조건 유사도·제외 조건 반영률·주의 쿼리 수를
추가했다.

조건 유사도는 같은 공간·대상의 실제 쿼리 중 기준 조건이 가장 많이 포함된 문장을 선택하고, 반영한
조건 수 / 전체 조건 수로 계산한다. 공백·기호·대소문자를 정규화하고 지정한 동의어를 허용한다. 조건은
한 실제 문장 안에서 확인한다. 별도의 모델 호출이나 임베딩 API는 사용하지 않는다. 제외 조건은 별도로
검사하고, 정정 전 색상·다른 사람 취향·불필요한 소유물 같은 지정 표현이 실제 쿼리에 나오면 주의
항목으로 표시한다. 추가 조건이나 모든 모순을 자동으로 판단하는 점수는 아니다.

이 수치는 페르소나 전체 설정과의 조건 일치도이며 자동 정답 평가나 추천 상품 품질 점수가 아니다. 합성
사용자가 아직 공개하지 않은 사실이나 편집한 고정 발화의 차이도 누락으로 표시될 수 있으므로 실제
사용자 발화와 함께 검토한다. 실행 시 기대 기준을 manifest에 저장하고 각 결과 및 최종 summary에
검토값을 보존한다. 기준이 없는 과거 실행에 새 기준을 덧씌우지 않는다. 새 기준을 사용하려면 관리
API·워커를 함께 재시작하고 업데이트된 페르소나로 새 실험을 실행한다.

## 모델 선정과 파인튜닝 검토 기준

8B·1B·30B는 확정 모델이 아니다. 기존 모델과 실제 서비스 프롬프트로 중요한 상황 10~15개를 먼저
확인한다. 대시보드의 테스트 실행·보드의 목적에 우선 검토할 상황 10개와 진행 순서를 안내한다. 이
목록은 수동 검토 기준이며 자동 평가셋이나 정답 점수가 아니다.

대화의 자연스러움, 반복 질문, 화자 구분, 단순 언급과 선호, 부정·정정, 정보 없음, 프로필·추천 쿼리를
확인한다. 실패는 프롬프트·추출·병합·쿼리 단계로 나누어 먼저 수정한다. 모델의 실패가 반복되고 더 큰
모델의 비용·지연이 부담될 때 파인튜닝을 검토한다. AI Hub 데이터셋은 필요해질 때 학습용으로 검토하고,
추가 페르소나 확장·대규모 학습 데이터 가공·학습 관리 기능은 아직 만들지 않는다.

## 실제 니쥬 서비스 테스트

테스트 실행의 기본 모드는 **니쥬 서비스**다. 이 모드와 직접 채팅에서 서비스의 `.env`와 프로세스
환경변수를 읽는다. 프로세스 환경변수가 우선하며, 선택 사항은 해당 실험에만 적용되고 `.env`는
수정하지 않는다.

니쥬 대화는 취미·일상 루틴뿐 아니라 경험·가치관·관계·선택의 이유·생활의 변화·미래 계획과 기대도
이야기한다. 사용자가 꺼낸 내용이 우선이며, 짧게 공감한 뒤 궁금한 것 하나를 묻는다. 새 관심사가
추출되지 않았다는 이유로 화제를 바꾸거나 부족한 추천 항목을 채우는 소재를 우선하지 않는다. 누적 추출
결과로 성격·가치관을 확인하도록 강제하는 것도 제거했다.

대화 이력과 취향 추출의 역할을 분리한다. 추출기는 기존 스키마에 맞는 근거 있는 취향만 추출하므로
모든 가치관·관계·미래 계획이 별도 프로필 필드로 저장되지는 않는다. 종료 의사·최대 턴·세션 종료
정책은 유지한다. 대화 방식은 하나(companion)만 남겼고 화면에서 고르지 않는다.

| 화면 설정      | 사용하는 서비스 설정                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------- |
| 응답·요약 모델 | `RESPONSE_MODEL_BASE_URL`, `RESPONSE_MODEL_NAME` 또는 등록된 연결                                   |
| 취향 추출 모델 | `EXTRACTION_MODEL_BASE_URL`, `EXTRACTION_MODEL_NAME` 또는 등록된 연결                               |
| 취향 판단 경로 | `JUDGMENT_MODEL_BASE_URL`, `JUDGMENT_MODEL_NAME`; 이번 실험에서 끄기 가능                           |
| 실제 임베딩    | `EMBEDDING_BASE_URL`, `EMBEDDING_QUERY_MODEL_NAME`, `EMBEDDING_SPACE_ID`, `EMBEDDING_DIMENSIONS` 등 |
| 실제 상품 추천 | `CATALOG_DATABASE_URL_RO` 우선, 없으면 `CATALOG_DATABASE_URL`                                       |

로컬 모델을 비교하려면 응답과 추출 각각 등록된 LM Studio·Ollama 연결을 선택한다. 판단 경로는
환경변수 기본값이므로 `JUDGMENT_MODEL_BASE_URL`이 원격이면 로컬 추출 모델을 선택해도 판단은 원격에서
수행된다. 로컬 직접 추출만 보려면 **판단 모델 끄기 · 직접 구조화 추출**를 선택한다.

사용자 발화를 한 줄에 한 턴으로 입력한다. 실제 API의 발화 길이 계약과 최대 20턴을 적용하며, 서비스가
대화를 종료하면 남은 입력을 강제로 진행하지 않는다. 시작 인사→턴별 응답·추출→분석·요약을 실행한다.
응답과 추출은 서비스처럼 병렬 처리한다. 각 실행은 별도의 메모리 세션을 사용하므로 운영 Redis·세션에
쓰기나 변경이 없다. 환경 설정이 대기 중 바뀌면 새 실험 생성을 요구한다.

추천 실행 범위:

- **쿼리 생성:** 실제 `recommendation_profile` → `recommendation_inputs` → `build_search_queries`를
  실행하고 검색 문장·검색 공간·self/gift 적용·제외·선호 문장을 표시한다. 임베딩 API와 DB는 호출하지
  않는다.
- **실제 임베딩:** 위의 입력을 실제 `OpenAICompatibleEmbedder`로 전달하고 차원·norm·일부 벡터를
  기록한다. 임베딩은 프로세스/`.env`의 `UPSTAGE_API_KEY` 설정을 사용한다.
- **실제 상품 추천:** 실제 `V1RecommendationService` / `RecommendationEngine` / PostgreSQL 카탈로그
  검색·랭킹을 실행한다. DB 연결에는 `default_transaction_read_only=on`을 적용한다. 임베딩 공간과
  차원은 카탈로그와 맞아야 한다. 미설정이면 실행 전에 오류를 표시하며 가짜 상품으로 대체하지 않는다.

검색 쿼리는 현재 서비스의 규칙 기반 로직이다. 별도 LLM 쿼리 생성 프롬프트를 만들지 않는다. 서비스
모드에는 자유 Temperature·토큰 슬라이더를 적용하지 않는다. 응답·추출 출력 상한과 timeout·재시도는
서비스 설정을 유지한다. 전체 실험 시간만 최대 1,800초까지 지정한다.

실험 이력의 각 단계에서 실제 요청 메시지·구조화 추출 스키마·원본 추출 결과·프로필 병합·추천 쿼리를
열어볼 수 있다. 추출이 실패해 서비스가 빈 델타로 계속 진행한 경우에도 실패를 표시한다. 자동 정답
점수는 아직 붙이지 않았으며, 초기 smoke 점수와 서비스 실행 결과를 구분한다.

기본 URL은 LM Studio `http://127.0.0.1:1234/v1`, Ollama `http://127.0.0.1:11434/v1`이다. 모델
다운로드·실행은 해당 런타임에서 한다. 모델 목록은 모델 적재·추론 성공을 보장하지 않는다.

## 원격 서버와 키

OpenAI 호환 `/models`, `/chat/completions`가 노출된 RunPod 연결을 추가할 수 있다. RunPod job 기반
native `/run` API는 이 어댑터의 대상이 아니다. 등록된 연결의 키는 서버와 워커의 환경변수로 설정하고
UI에는 변수 이름만 입력한다. 서비스 모드의 환경변수 기본 모델은 `.env`/환경변수의 `MODEL_API_KEY`
또는 `OPENROUTER_API_KEY`를 사용한다. 등록 연결로 대체하면 그 연결의 키만 사용한다. 관리 앱은
자격증명 값·provider 오류 응답을 기록하지 않는다.

API key 환경변수 이름 예시: `AI_LAB_RUNPOD_KEY`. 임의의 기본 placeholder key를 보내지 않는다. UI의
입력·출력 기록은 테스트용 합성 데이터에 사용한다. JSON export에는 입력·출력이 포함되며, CSV에는
측정·판정 데이터만 포함된다. 이력 삭제는 해당 실행의 표본도 삭제한다.

## 지표의 해석

- 첫 청크 지연은 클라이언트 측정이다. 서버 TTFT 및 니쥬 사용자 화면 지연과 다르다.
- 성공 지연의 p50/p95를 계산하고 실패 요청도 성공률 분모에 포함한다.
- usage가 빠지면 토큰 처리량을 추정하지 않는다.
- 요청 성공과 JSON 스키마·내용 정답 일치는 별도 지표다.
- 부하 테스트는 고정 동시성 closed-loop이며 open-loop 요청 유입률 테스트가 아니다.
- RunPod에서 다시 측정하기 전에는 로컬 결과로 운영 성능을 확정하지 않는다.
- 중단된 작업은 자동 재실행하지 않는다. 워커 재시작 시 interrupted 상태로 남긴다.
- 클라이언트 취소는 provider의 연산·과금 즉시 종료를 보장하지 않는다.
